# F3 性能实验第二轮执行方案

本文面向刘兆钰，说明第二轮 F3 性能实验的程序、计数、Vivado 运行、结果检查和材料整理方法。现有三类程序、9 组正式结果继续保留，作为第一轮基线；第二轮采用四类程序、三个 CPU 版本，共 12 组正式测试。

第二轮实验需要回答两个问题：

1. 单周期 CPU 与流水线 CPU 在不同指令特征下各有什么性能表现；
2. BTFNT 静态分支预测能否降低流水线的错误预测开销。

实验结果必须来自相同机器码、相同输入和相同计数边界。程序不能因为 CPU 版本不同而调整，也不能只保留对流水线有利的数据。

## 1. 版本与测试矩阵

每个程序运行以下三个版本：

| 版本标识 | CPU | 预测设置 |
| --- | --- | --- |
| `single` | 原单周期 CPU | 不适用 |
| `pipeline_off` | 五级流水线 CPU | `PREDICT_EN=0` |
| `pipeline_on` | 五级流水线 CPU | `PREDICT_EN=1` |

四类程序如下：

| 程序标识 | 正式名称 | 建议规模 | 主要观察内容 |
| --- | --- | ---: | --- |
| `independent_long` | 长无依赖运算流 | 240 条 ALU 指令 | 流水填充后稳定吞吐 |
| `dependency_long` | 连续数据依赖 | 128 条 RAW 依赖指令 | 无通用前递时的暂停开销 |
| `btfnt_loop` | BTFNT 长循环 | 256 轮后向循环 | 分支预测的直接收益 |
| `sort32_reverse` | 32 元素逆序冒泡排序 | 32 个元素 | 数据相关与控制相关共同存在时的综合表现 |

正式矩阵为 `4 个程序 × 3 个版本 = 12 组`。每组连续运行两次；两次计数与最终结果必须完全一致，第二次结果不重复写入主表，但原始日志要保留。

## 2. 四类程序的具体要求

### 2.1 长无依赖运算流

静态展开 240 条 `addi` 指令，每条指令只读取 `x0`。目标寄存器在 `x1` 至 `x30` 之间循环使用，相邻指令避免写同一个寄存器。程序末尾放置统一的结束标记 `jal x0, finished`。

生成逻辑可以采用：

```text
for i = 1..240:
    rd  = ((i - 1) mod 30) + 1
    imm = ((i - 1) mod 31) + 1
    emit addi rd, x0, imm
emit finished: jal x0, finished
```

正确性检查至少验证最后一轮写入的三个寄存器，不能只检查程序是否到达结束 PC。按上述生成规则，结束时应有 `x28=21`、`x29=22`、`x30=23`。该程序不应产生数据暂停，也没有条件分支。它用来观察流水线进入稳定阶段后的 CPI，240 条指令加结束标记仍能放入当前 256 字 ROM。

### 2.2 连续数据依赖

第一条指令执行 `addi x1, x0, 1`，随后连续执行 127 条 `addi x1, x1, 1`，最后放置结束标记。

```asm
addi x1, x0, 1
# 重复 127 次
addi x1, x1, 1
finished:
jal  x0, finished
```

结束时必须满足 `x1=128`。该程序用于量化 RAW 相关造成的暂停，不用于展示分支预测，因为它没有条件分支。报告中应同时给出暂停周期和 CPI，并指出当前流水线没有通用数据前递。

### 2.3 BTFNT 长循环

使用 256 轮后向条件分支。循环体保持短小，避免引入存储访问，使预测收益容易解释。

```asm
addi x1, x0, 0
addi x2, x0, 256
loop:
addi x1, x1, 1
blt  x1, x2, loop
finished:
jal  x0, finished
```

结束时必须满足 `x1=256`。动态条件分支应为 256 次。BTFNT 开启时，前 255 次向后跳转应预测为跳转，最后一次退出循环会错误预测；关闭预测时，前 255 次实际跳转均会错误预测。因此，正常预期为：

| 配置 | 条件分支 | 预期错误预测 |
| --- | ---: | ---: |
| 流水线预测关 | 256 | 255 |
| 流水线预测开 | 256 | 1 |

Mac 上的 RTL 预验证曾得到 `1799→1546` 周期、`255→1` 次错误预测，周期减少约 14.1%。这组数字只能作为排错参照，正式报告必须填写本次 Vivado 日志重新得到的结果。

### 2.4 32 元素逆序冒泡排序

沿用现有五元素排序的指令结构，将数组扩大到 32 个元素。正式输入为：

```text
32, 31, 30, ..., 2, 1
```

程序中的数组末地址由 16 改为 124，数组总字节数由 20 改为 128。核心结构可按下列汇编调整：

```asm
addi x0,x0,0
xor  t2,t2,t2
addi s0,t2,128
ori  t0,t2,0
jal  end1
L1:
addi t1,t2,124
jal  end2
L2:
lw   a0,0(t1)
lw   a1,-4(t1)
bge  a0,a1,endif
sw   a1,0(t1)
sw   a0,-4(t1)
endif:
addi t1,t1,-4
end2:
blt  t0,t1,L2
addi t0,t0,4
end1:
blt  t0,s0,L1
finished:
jal  x0,finished
```

结束时逐项检查数据存储器前 32 个字是否为 `1, 2, ..., 32`。只检查首尾元素不够，因为中间位置仍可能排序错误。

Mac 上的 RTL 预验证曾得到以下排错参照：预测关闭 7840 周期、预测开启 7378 周期，错误预测由 528 次降至 33 次，周期减少约 5.9%。Vivado 正式结果可能因程序镜像或计数实现调整而略有变化，应以本轮日志为准。

如果时间允许，可另测随机和已排序输入，用于附表验证输入分布的影响。主表只放逆序输入，不把三种输入拆成三个测试类别。

## 3. 程序和测试平台改动

在现有 `cpu/performance` 目录上扩展，不覆盖第一轮结果。

1. 在 `programs/build_programs.py` 中生成四组新镜像，并同步生成便于人工检查的 `.asm` 文件。
2. 在 `programs/cases.tsv` 中增加四个新测试项。每项记录程序标识、`TEST_ID`、结束 PC、指令镜像和数据镜像。
3. 在两个 testbench 的 `check_result` 中增加四种结果检查。
4. 流水线 testbench 输出周期、退休指令、暂停、条件分支和错误预测；单周期 testbench 输出周期、退休指令和条件分支，错误预测保持 `-1`。
5. 将两个 testbench 的超时上限提高到至少 20000 个仿真周期。现有 `200000 ns` 只够约 2000 个 10 MHz 周期，会在 32 元素排序完成前误报超时。
6. 将新一轮输出放到 `results/f3_round2/`，不得覆盖 `results/f3/` 中已经归档的第一轮 9 组结果。
7. 汇总脚本将程序集合改为四项，并检查正式结果恰好包含 12 个不重复的 `(version, program)` 组合。

建议先只加入 `btfnt_loop`，确认汇编编码、跳转偏移、结束 PC 和结果检查正确；随后再加入另外三项。这样遇到问题时容易定位。

## 4. 统一计数规则

四类程序和三个 CPU 版本必须采用同一语义边界：

- 起点为 PC=0 的第一条测试指令开始执行。流水线从该指令首次取指的周期开始计数；
- 终点为结束标记指令完成。流水线使用 `retire_valid && retire_pc==END_PC`，单周期在对应结束标记指令执行完成后停止；
- 周期数包含流水填充、真实暂停、分支冲刷和结束指令完成前的流水排空；
- 不包含复位、UART 收发、等待输入和结束死循环的后续重复执行；
- 动态指令数只统计真实完成的指令，包括有效分支、存储和写 `x0` 的指令；
- 空泡、暂停等待周期和错误路径指令不计入退休指令数；
- 分支数只统计已完成的条件分支，`jal` 不计入 BTFNT 条件分支统计；
- 单周期 CPU 没有预测器，错误预测写 `N/A`，原始数值继续使用 `-1`，不能写成 0。

计数器要在复位期间清零。结果检查通过后再输出 `F3_PASS`；只到达结束 PC、但寄存器或存储器结果错误时必须让仿真失败。

## 5. Vivado 执行顺序

在装有 Vivado 2019.2 的 Windows 电脑上，从仓库根目录操作。

### 5.1 同步与记录版本

```powershell
git pull --ff-only
git status --short
git rev-parse HEAD
```

开始实验时工作区应没有与 F3 相关的未提交修改。将提交号写入本轮 `metadata.txt`。

### 5.2 生成并人工检查程序

```powershell
python cpu/performance/programs/build_programs.py
```

生成后检查：

- 每个指令镜像为 256 个 32 位字；
- 结束 PC 与 `cases.tsv` 一致；
- `btfnt_loop` 的分支立即数指向较小地址；
- `sort32_reverse` 的数据镜像前 32 个字为 32 到 1；
- 其余未使用空间按当前约定填充。

### 5.3 先跑一组冒烟测试

先运行 `pipeline_on + btfnt_loop`。确认结果为 `x1=256`、条件分支 256 次、错误预测接近预期的 1 次。若这一组不通过，先检查跳转编码、结束 PC、分支计数更新时刻和流水线排空边界，不要直接运行完整矩阵。

### 5.4 运行 12 组正式矩阵

将现有 `run_f3_vivado.tcl` 扩展为第二轮输出目录后执行：

```powershell
vivado -mode batch -source cpu/performance/scripts/run_f3_vivado.tcl
python cpu/performance/scripts/summarize_results.py
```

完整矩阵第一次通过后，再运行一次。第二次运行前保存第一次的原始目录，或者让脚本自动写入带 `run1`、`run2` 后缀的目录。两次运行需要满足：

- 12/12 功能检查通过；
- 每组周期、退休指令、暂停、分支和错误预测完全一致；
- 同一程序在三个版本上的退休指令数一致；
- `time_ns = cycles × 仿真时钟周期`；
- 日志中没有 `$fatal`、超时、未知值导致的结果绕过或内存越界警告。

### 5.5 保留频率证据

现有实现后时序报告表明单周期核心和流水线核心均满足 50 MHz。第二轮如果没有修改 CPU RTL，可引用现有报告，同时记录本轮提交号；如果修改了流水线架构，例如增加前递或改变分支重定向路径，则必须重新运行综合、布局布线和时序检查，旧报告不能继续代表新设计。

## 6. 正式记录字段与计算

每一组至少保存：

```text
提交号、Vivado版本、CPU版本、程序、输入、正确性结果、
周期数C、退休指令数N、CPI、暂停周期、条件分支数、
错误预测数、时钟周期Tclk、CPU时间、相对单周期加速比
```

计算公式：

```text
CPI = C / N
CPU时间 = C × Tclk
相对单周期加速比 = 单周期CPU时间 / 当前版本CPU时间
预测加速比 = 预测关闭流水线周期 / 预测开启流水线周期
周期减少率 = (预测关闭周期 - 预测开启周期) / 预测关闭周期
错误预测率 = 错误预测数 / 条件分支数
```

分支预测开关的比较在同一个流水线实现、相同时钟频率下进行，因此预测加速比可直接用周期数计算。单周期与流水线的 CPU 时间应同时提供两种视图：

1. **统一 50 MHz 对照**用于比较相同频率下的 CPI、暂停和冲刷开销；
2. **课程配置频率对照**使用单周期 10 MHz、流水线 50 MHz，只能标为配置频率下的系统时间。

现有时序数据中，单周期核心 50 MHz 的 WNS 为 `+6.080 ns`，流水线核心 50 MHz 的 WNS 为 `+5.984 ns`。因此，课程配置对照不能写成“流水线最高频率是单周期的 5 倍”。

## 8. 结果分析口径

四类测试分别支持以下分析：

- 长无依赖运算流说明流水线填充开销随程序增长被摊薄，接近稳定吞吐；
- 连续数据依赖量化当前无通用前递造成的暂停，是流水线 CPI 偏高的主要来源；
- BTFNT 长循环直接展示后向跳转预测，将大多数已执行分支从错误预测转为正确预测；
- 32 元素逆序排序同时包含加载、存储、数据相关和条件分支，更接近综合应用。预测仍有收益，但收益会被数据暂停和循环边界分支稀释。

如果统一 50 MHz 下流水线仍慢于单周期，应如实写出。改变测试程序只能帮助观察不同瓶颈，不能证明当前架构拥有更高最高频率。若答辩必须展示流水线架构本身的性能优势，需要先增加数据前递、缩短分支重定向关键路径，再用同一套四类程序和新的实现后时序重新测试。
